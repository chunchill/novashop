# 本体 · DDD · OO · E-R · 微服务：正本清源

> **写给谁**：做业务系统的程序员与架构师。不需要哲学课基础。  
> **想说清什么**：这些方法为什么会出现（存在即合理）、各自解决什么问题、为什么会彼此较劲（既生瑜何生亮）、又为什么常常要**组合使用**。  
> **怎么读**：先读 §1–§4 建立直觉；做方案时再翻 §5–§7。

---

## 1. 先把话说透

很多人一上来就问：「我们到底用 DDD 还是微服务？要不要上 Ontology？类是不是要和表一一对应？」

这些问题本身就容易把人带偏。更贴生活的问法是：

1. **它当初是为了治什么病才出现的？**（存在即合理）  
2. **它擅长治什么，不擅长治什么？**  
3. **和别的方法叠在一起时，哪里会打架？打架能不能变成分工？**（既生瑜何生亮）

结论可以先记这三句：

- **五者不是五选一**，而是不同层上的工具。  
- **会组合使用**才是常态：同一套下单功能里，往往同时有表、类、领域规则、服务边界，有时还有企业操作层。  
- 正本清源，是为了**用对地方**，不是为了背术语。

| 方法 | 一句话 |
|------|--------|
| **E-R** | 把该记住的事实，结构清楚地存下来 |
| **OO** | 把规则和行为，组织进能协作的代码结构里 |
| **DDD** | 先把业务语言和边界谈清楚，再在边界里保护规则 |
| **微服务** | 按可独立演进的单元拆部署、拆团队、拆故障域 |
| **Ontology（以 Foundry 为代表）** | 在多系统之上，让人和系统能「看见同一世界」并**受治理地行动** |

---

## 2. 存在即合理：它们各自从什么痛里长出来

方法能留下来，多半是因为当时有一批人被同一类问题反复折磨。

### 2.1 E-R：数据说不清、对不齐

早期系统里，层次库、网状库、关系库各说各话，业务上「客户—订单」这种常识，到实现层就丢了。E-R（陈品山等）要做的事很朴素：**先用大家听得懂的「实体、属性、关系」把信息结构谈清楚**，再落到具体库表。

它合理，因为没有稳定的数据形状，报表、对账、约束都站不住。

### 2.2 OO：规则一复杂，过程式代码就塌

业务规则变多以后，到处 `if/else` 的脚本会失控：改一处坏三处，也测不清。面向对象把**数据和操作它的行为放在一起**，用封装、协作、替换来管复杂度。

它合理，因为软件不只是「存数据」，还要「按规矩改数据」。

Fowler 后来提醒：如果对象只有 getter/setter，逻辑全在 Service 里，那叫**贫血模型**——付了对象映射的成本，却没吃到对象组织行为的红利。简单 CRUD 用事务脚本完全合理；复杂多变的规则，才值得上富领域模型。

### 2.3 DDD：技术分层很漂亮，业务仍然糊成一团

分层、框架都有了，可「订单」在销售、财务、仓储嘴里根本不是一个意思；规则散落在 Controller、Service、SQL 和口头约定里。Evans / Vernon 强调的不是多造几个 Entity 注解，而是：

- 先有**统一语言**；  
- 再划**限界上下文**（这里说的 Order，就按这里的定义走）；  
- 上下文里再用聚合等手段保护不变式。

它合理，因为复杂业务的第一敌人往往不是「不会写类」，而是**词义混乱、边界失踪**。

### 2.4 微服务：单体在组织和发布上撑不住了

系统变大以后，全体一起发版、一起宕机、跨团队改同一仓库，成本会爆炸。微服务要解决的是**独立部署、故障隔离、团队自治**（Newman 等）。它和 DDD 常一起出现，因为「按业务边界拆」比「按表拆」靠谱得多；但微服务本身回答的是运行时与组织问题，不是自动给你正确领域模型。

它合理，因为规模到了一定程度，**演进速度和故障范围**本身就是需求。

### 2.5 Ontology（Foundry）：系统很多，人却看不见、动不了

企业里 OMS、WMS、CRM、数仓各有一套真相。分析平台能出报表，却很难在同一套语义下**做完决策并写回业务系统**；人和 AI 更难共享一个「可操作的世界」。Palantir 把 Ontology 放在数字资产之上，做成**操作层 / 数字孪生**：对象和链接负责「看见」，Action、函数、安全负责「能动且可追责」。

它合理，因为大组织的痛常常不是缺一张表，而是**跨系统决策环断了**。

### 2.6 小结

| 方法 | 当初主要在治的病 |
|------|------------------|
| E-R | 信息结构混乱、无法对齐 |
| OO | 复杂行为无法在代码里安顿 |
| DDD | 业务语言与边界混乱，规则无处安放 |
| 微服务 | 发布、团队、故障域无法随规模演进 |
| Ontology | 跨系统看不见、决策做不成、行动不可治理 |

**存在即合理**：每一种都对应真实痛点。没有「落后方法」——只有「用错层」。

## 3. 正本清源：建模其实总在做四件事

先别管商标。任何建模，骨子里都在处理这四件事——这就是程序员版的「第一性原理」，来自干活本身，不是来自哲学教材：

| 你在做的事 | 人话 | 例子 |
|------------|------|------|
| **表示** | 给世界里的东西起名、结构化，让计算机能处理 | 一行订单、一个 Order 对象、一个 Ontology Object |
| **边界** | 规定这套说法在哪里成立、出了界就不算 | 一张库、一个模块、一个限界上下文、一个服务、一套操作层 |
| **规矩（不变式）** | 规定哪些状态变化是禁止的 | 外键、对象不变量、「下单不得超过信用额度」 |
| **闭环行动** | 谁、在什么条件下、如何改世界，并且留得下痕迹 | 事务、领域命令、API、Ontology Action + 写回 |

为什么会「既生瑜何生亮」？因为**每种方法往往把其中一两项做得特别强，并默认另外几项「别处有人管」**：

| 方法 | 通常特别强 | 你若只用它，容易缺什么 |
|------|------------|-------------------------|
| E-R | 表示（数据结构） | 业务该不该做、跨团队词义 |
| OO | 规矩落在代码协作里 | 企业级语言边界、跨进程责任 |
| DDD | 边界 + 规矩 | 怎么部署、跨系统怎么统一看见 |
| 微服务 | 边界（运行时/组织） | 领域深度（若乱拆）、操作层语义 |
| Ontology | 看见 + 治理行动 | 若当唯一真相库，会冲掉各服务里的权威规矩 |

开会吵起来时，先问一句就够了：**我们现在破的是表示、边界、规矩，还是行动闭环？** 对上了，该请谁上场就清楚了。

## 4. 各自解决什么：边界与误用（程序员版）

### 4.1 E-R

**解决**：权威数据如何结构化存储、查询、保证完整性。  
**常见落地**：概念模型 → 逻辑模型 → 物理表（索引、分区另说）。

**用对**：每个服务/上下文内部的库，值得认真做 E-R。  
**用错**：画一张「全公司大 ER」，再按表拆微服务——等于用数据形状指挥组织和部署。

### 4.2 OO

**解决**：代码里如何组织复杂行为，使修改与测试可控。  
**要点（Fowler）**：规则简单 → 事务脚本也行；规则复杂多变 → 行为进领域对象，应用服务变薄。

**用对**：在一个服务内部，用对象表达「能做什么、不能做什么」。  
**用错**：把类图当成战略设计；或复杂域上坚持贫血模型却上很重的 ORM。

### 4.3 DDD

**解决**：复杂业务如何谈清楚语言与边界，并在边界内保护规则。  
**战略**比战术重要：统一语言、限界上下文、上下文之间怎么翻译（防腐层等）。  
**战术**：实体、值对象、聚合、领域事件——用来落实规矩，不是用来炫技。

**用对**：核心域、规则多、变化快的地方。  
**用错**：CRUD 后台硬套全套战术；「每个类一个聚合」「每个聚合一个微服务」。

业界常见提醒（Vernon）：满嘴 Aggregate、不谈上下文和语言，等于没摸到 DDD。

### 4.4 微服务

**解决**：如何独立发布、隔离故障、匹配团队结构。  
**和 DDD 的健康接法（Azure 等实践）**：

- 服务功能尽量别跨多个限界上下文；  
- 粒度大致在「不小于一个聚合、不大于一个上下文」；  
- 拿不准先粗后细——拆开比合并容易；  
- 同一聚合的状态机，尽量放在同一个服务里。

**用对**：有真实的独立演进压力时。  
**用错**：按表/按类/按 Ontology 对象机械拆；共享数据库当集成总线；为了「微服务数量」牺牲内聚。

模块化单体完全合法：先按上下文分模块，真需要再抽进程。

### 4.5 Ontology（Foundry）

**解决**：跨系统如何形成可导航的业务对象世界，并让决策在治理下执行、写回。  
**它不是**：薄语义层、指标平台、或「升级版 ER 图」。  
**官方坚持**：建模真实世界，不要把源系统表原样搬成对象；Action 管人/Agent 的决策，管道管批量加工。

**用对**：多系统并存、要 360° 看见、要受控写回、要人机协同决策时。  
**用错**：全表 ontologize；部门各造一套 Customer；Action 只改投影、权威服务不知情（双主库）。

## 5. 既生瑜何生亮：为什么会打架，又为什么能一起用

「瑜」和「亮」都强，就会抢功——方法也一样。关键几处张力如下；每一处都可以变成**分工**而不是站队。

### 5.1 E-R vs OO：表和对象长得不像

**张力**：表喜欢扁平、范式；对象喜欢行为与图结构。  
**分工**：复杂规则以领域模型为准，表是映射结果（Data Mapper / Repository）；简单系统两者可以长得很像。  
**生活类比**：户口本上的栏目，不必等于你这个人实际会做的事——但办事时两者都要用。

### 5.2 DDD vs 微服务：模型边界 vs 进程边界

**张力**：上下文是「说法与规矩」的边界；服务是「部署与故障」的边界。常对齐，但不等于同一个东西。  
**分工**：DDD 先定谁说了算；微服务再定怎么发版。聊天式互相调用，多半是拆错了，该合并。  
**生活类比**：公司部门职责（上下文）和办公楼分区（部署）相关，但不是一回事。

### 5.3 DDD vs Ontology：多真相 vs 一张可导航的地图

这是最容易吵、也最值得想清楚的一对。

- DDD：**销售的 Customer 和财务的 Customer 可以不是一个模型**——否则假装统一，会出假确定性。  
- Ontology：**操作层希望大家能顺着链接找到「这个客户」**——否则跨系统决策做不动。

两者都合理，所以像瑜亮：一个护「局部说清楚」，一个护「全局找得着」。

**推荐合用法**（也是业界务实做法）：

1. **规矩的权威**仍在各限界上下文 / 微服务里（例如信用校验在订购服务）。  
2. 对外只暴露稳定契约（API、事件、ID）。  
3. Ontology 做**投影与导航**（管道/CDC 汇聚），不假装自己是唯一写库。  
4. Ontology 的 Action 是**治理入口**：校验权限与条件 → 调用权威服务或写回 → 更新投影。  
5. 操作层可以有一个「规范客户身份」方便导航；各上下文内部模型通过 ID 与防腐层对齐即可。

记住两句人话：

> **DDD 管「谁说了算」。**  
> **Ontology 管「谁都能找到，并在规矩下行动」。**

### 5.4 微服务 vs Ontology：写权威 vs 操作面

**张力**：服务要私有库；Ontology 要统一看见。  
**分工**：服务拥有写入真相；Ontology 负责读投影 + 受控写回。Object type ≠ 微服务；一个服务可投影多个对象，一个对象也可合并多源，但**写回路径必须清楚**。

### 5.5 一张组合图（你平时真正会落到的样子）

```text
        人 / 前端 / Agent
                │
                ▼
     ┌── Ontology（可选）──┐
     │  看见对象 · 治理动作  │
     └───┬────────────┬────┘
         │投影         │写回
         ▼             ▼
   ┌──────────┐   ┌──────────┐
   │ 服务 A    │   │ 服务 B    │
   │ DDD+OO   │◄─►│ DDD+OO   │
   │ 私有库ER │   │ 私有库ER │
   └──────────┘   └──────────┘
```

没有 Ontology，前四者照样能组合（很多团队就是这样）。有了 Ontology，是在上面多加一层**跨系统操作面**，不是替换下面的权威。

## 6. 同一个例子：五镜头同时成立

业务规则：**下单金额不得超过剩余信用额度；通过则保存订单。**

| 镜头 | 它在忙什么 |
|------|------------|
| **E-R** | `customer`、`order` 表怎么建、键怎么挂 |
| **OO** | `reserveCredit` / `placeOrder` 这类行为放哪，避免只有 setter |
| **DDD** | 「信用」「下单」在哪个上下文说了算；跨上下文怎么查/怎么发事件 |
| **微服务** | `ordering-service` 写订单；信用同步查或本地副本；不 join 对方库 |
| **Ontology** | 订单/客户对象可导航；`PlaceOrder` Action 带权限与校验；提交后写回订购权威 |

五镜头叠在一起，才既「算得对」，又「发得了版」，还能「运营侧看得见、动得了」。  
这就是：**存在即合理，而且常常要一起用。**

## 7. 怎么正确使用：开会语言、踩坑、落地顺序

### 7.1 会上吵什么，就用谁的语言

| 你们在吵 | 先请谁上场 |
|----------|------------|
| 表、键、索引、迁移 | E-R |
| 类怎么拆、依赖朝哪、怎么测 | OO（可加六边形/整洁等） |
| 「这个词两边是不是一个意思」 | DDD 战略 |
| 怎么拆服务、谁发版、故障域 | 微服务（边界尽量跟上下文走） |
| 跨系统 360°、受控写回、人机决策 | Ontology |
| 要不要上富领域模型 | 看规则复杂度；简单 CRUD 别硬上 |

### 7.2 常见踩坑（都是「用错层」）

| 踩坑 | 为啥疼 | 怎么改 |
|------|--------|--------|
| 表 → 类 → 服务 → Object 一一对应 | 用数据形状指挥一切 | 从业务语言和决策反推 |
| 微服务 + 共享库 | 分布式单体 | 私有数据；用 API/事件集成 |
| 只会堆 Aggregate 注解 | 没边界的战术表演 | 先上下文和语言 |
| 复杂域贫血 + 重 ORM | 成本高、收益低 | 行为回领域，或老实用事务脚本 |
| Ontology 当第二写库 | 双真相 | Action 必须打到权威服务 |
| 用上下文消灭企业导航 | 跨部门啥也串不起来 | 保留上下文模型 + 操作层投影 |
| 用企业大对象消灭上下文 | 假统一、真耦合 | 投影可规范，实现可多模型 |

### 7.3 落地顺序（可剪裁）

**新业务大致可以：**

```text
先谈清楚决策和语言（DDD 战略）
  → 边界里把规矩做成模型（DDD 战术 + OO）
  → 服务内把库建好（E-R）
  → 需要独立演进再拆进程（微服务；可先模块化单体）
  → 需要跨系统看见/治理行动再上 Ontology
```

**老系统大致可以：**

```text
先画清「谁是写权威」
  → 新核心域用防腐层保护
  → 逐步抽服务，别第一天按表拆光
  → Ontology 先做高价值对象的可导航投影
  → 再少量 Action 写回，避免一天 ontologize 全库
```

### 7.4 三条自检（不靠玄学）

做方案时用这三条戳自己，比站队有用：

1. **边界先于名字**：说得出「这个词在哪个团队/上下文里成立」吗？说不出，先别急着建表/建对象。  
2. **规矩跟着权威走**：这条业务规则，唯一执行点在哪个服务？投影层有没有另搞一套相反逻辑？  
3. **闭环先于摆设**：关键决策有没有「数据 + 逻辑 + 能做的动作 + 谁能做」？还是只在堆对象类型数量？

## 8. 收束

回到开头那句生活里的道理：

- **存在即合理**——E-R、OO、DDD、微服务、Ontology 各自治过真病，所以都还在。  
- **既生瑜何生亮**——它们优化点不同，叠在一起会抢戏；抢戏不可怕，可怕的是不知道在抢什么。  
- **程序员要正本清源**——不为背哲学名词，为的是：看清痛点、选对层、敢组合。

再浓缩成一句可放进分享页的话：

> 用 E-R 把事实存清楚，用 OO 把行为写清楚，用 DDD 把语言和规矩谈清楚，用微服务把演进和故障域拆清楚，用 Ontology（若需要）把跨系统的看见与行动治理清楚。  
> 它们是工具箱，不是宗教；组合使用，才是软件开发里的常态。
